## 二、可用性指标

| 指标 | 目标 | 实现机制 |
|---|---|---|
| **系统整体可用性** | ≥ 99.99%（年 downtime ≤ 52.6 分钟） | 前端 EdgeOne 多地域 + 后端双 AZ + K8s 自动漂移 + 故障自愈 |
| **前端 SPA 可用性** | ≥ 99.995% | EdgeOne Pages 多地域 + 版本回滚 1 键 + CNAME 切灾备 60 秒 |
| **登录 API** | ≥ 99.99% | P0 级：3 副本 + 独立限流 + Redis 脱机时降级（短期内存 Session，15 分钟自动切回） |
| **财务写 API** | ≥ 99.95% | P0 级：双 AZ 主库 + 半同步复制（至少 1 从提交成功才算成功，防单机丢数据） |
| **其他业务 API** | ≥ 99.9% | P1 级：HPA 扩缩 + 只读副本分流读请求 |
| **RPO（数据丢失容忍）** | **≤ 15 分钟** | binlog 同步到从库 + 每 5 分钟 binlog push COS，最坏丢失 5 分钟 |
| **RTO（恢复时间）** | **≤ 1 小时** | 主库挂了 → 从库提升（≤5 分钟） + 业务验证（≤20 分钟）+ 切 DNS（≤30 分钟传播） |
| **冷备恢复 RTO** | ≤ 4 小时 | 上海全挂 → 广州冷备启计算 + 导入最新快照 binlog |

## 三、前端 EdgeOne Pages 高可用（2 层容灾）

### 3.1 版本管理 & 回滚

| 动作 | 操作步骤 | 风险 |
|---|---|---|
| **上线新版本** | 1. 本地打 ZIP（本项目 _output/ 目录）<br/>2. EdgeOne Pages → 项目 → 部署管理 → 上传新版本<br/>3. 「灰度 10% 流量」测试 30 分钟，冒烟 14 页全通过<br/>4. 100% 全量<br/>5. 同时把同一份 ZIP 上传到 COS `versions/troupe-vYYYYMMDD-HHmm.zip`（带版本号） | 灰度期如有 4xx/5xx 暴涨，立即回滚 |
| **一键回滚** | EdgeOne Pages → 项目 → 部署管理 → 历史版本 → 「发布」上一个稳定版本 | RTO ≤ 2 分钟 |
| **版本保留策略** | 最近 30 个版本在 EdgeOne Pages 保留；>30 个删除；但 COS 所有历史版本永久保留 | 防止 EdgeOne 版本超限被自动清理 |

### 3.2 前端双地域容灾（上海主 / 新加坡备）

1. 新加坡 EdgeOne Pages 另建一个项目（同名），每次上海发布成功后 **10 分钟内** 同样上传一份同 ZIP 发布
2. DNS 配置（腾讯云 DNSPod / Cloudflare DNS）：
   - 主记录：`admin.your-troupe.com CNAME → shanghai-xxx.edgeone.app`（健康检查：`GET https://shanghai-xxx.edgeone.app/healthz.txt` 每 60s，连续 3 次失败自动下线）
   - 备记录：同域名 CNAME → `singapore-xxx.edgeone.app`（平时权重 0；主挂了权重自动升 100）
3. 前端静态根目录放一个 `healthz.txt`（内容 `ok`，永不改），给 DNS 健康检查用（EdgeOne Pages 默认允许 .txt）

### 3.3 前端脱机（后端 API 全挂）降级方案

前端 `Admin.request` 拦截器里加：连续 5 次 5xx / 超时 → 自动切换到 **只读本地缓存模式**（localStorage 里最近一次成功响应的快照），顶部红条提示：
```
⚠️ 后端 API 暂时无法访问，当前展示为本地快照（数据可能已过期）。您可以继续浏览，但所有写操作已暂停。
预计恢复时间：请关注管理员通知 · 技术支持：{运维电话}
```

- 所有写按钮置灰（新增/编辑/删除/导出），只读可看
- 右上角加「刷新重试」按钮（手动切回）
- 后端恢复后 30 秒内自动检测并恢复正常模式

## 四、后端 API 层高可用

### 4.1 部署规格（最低生产配置）

| 层级 | 规格 | 数量 | 用途 |
|---|---|---|---|
| Nginx / CLB | 腾讯云 CLB 性能型（或同规格自建 Nginx 2 台 + keepalived） | 2 VIP | TLS 卸载 + WAF + 限流 + 路由 |
| API 计算（K8s Deployment） | 4C8G（腾讯云 S5.MEDIUM4 / 阿里云 g6.xlarge） | **3 台起**（容忍 1 台挂，仍 2 台服务） | 跑 Node/Go/PHP/Python 业务 API |
| HPA 扩缩阈值 | CPU ≥ 65% 或 P99 ≥ 800ms → 加 1 台；CPU ≤ 20% 10 分钟 → 减到 3 台（下限） | 最大 20 台 | 应对年末汇演高峰（演出订单/考勤工资导出暴涨） |
| MySQL | 腾讯云 MySQL 高可用版（8C32G + 1TB SSD，双 AZ + 灾备只读） | 1 主 + 1 同 AZ 从（半同步） + 1 跨地域灾备从（异步） | 主业务库 |
| Redis Cluster | 腾讯云 Redis 集群（4G×3主3从） | 6 节点 | Session 黑名单 + 限流 + 业务缓存 + 登录锁定计数器 |
| COS / OSS | 标准存储（近线归档冷数据 180 天自动转） | 2 桶（上海 COS + 广州 COS 双写）+ 1 桶（阿里云 OSS 跨云冷备） | 文件 + 备份 + binlog |

### 4.2 健康检查 & 故障自愈

```
K8s Liveness 探针：GET /api/healthz/live  → 200 "live"（进程存活，连续 3 次失败重启 Pod）
K8s Readiness 探针：GET /api/healthz/ready → 200 {"db":true,"redis":true,"diskFreePct":78}（依赖全部正常才接流量；失败即摘除）
CLB 健康检查：同 Readiness，间隔 5s，2 次成功上线，3 次失败下线（RTO 切换 ≤ 30s）
```

### 4.3 数据库主从切换（MySQL）

#### 正常故障（主机宕机 ≤ 5 分钟内）

1. 云厂商托管版自动切换（腾讯云高可用版默认 < 30 秒完成，VIP 漂移，业务无感）
2. 自建 MySQL：Keepalived + orchestrator，切换步骤 ≤ 5 分钟
   ```
   orchestrator-client -c begin-maintenance --alias troupe-master
   orchestrator-client -c graceful-master-takeover --alias troupe-master   # 选最延迟从库升主
   orchestrator-client -c complete-maintenance --alias troupe-master
   ```
3. 切换后 10 分钟内必须检查：
   - SHOW SLAVE STATUS（新从库复制是否 OK，Seconds_Behind_Master < 5s）
   - 财务接口自测 `POST /v1/admin/fin-ledger/test-write`（测试凭证，写后立即作废）
   - 随机抽 3 个业务查询，检查结果与切换前一致

#### 跨地域灾备（上海全 AZ 故障 ≤ 1 小时）

1. 人工或自动（监控连续失败 10 分钟 + 电话确认）触发广州灾备提升主库
2. 导入上海最近的 binlog（最坏丢失 ≤ 5 分钟）
3. 后端 API 广州冷备 2 台启动（从 0 → Ready 约 8 分钟）
4. DNSPod：`admin.your-troupe.com` 的后端 API CNAME 切到广州 CLB（TTL = 60，传播 ≤ 15 分钟）
5. 冒烟 14 页全通过 → 通知业务恢复
6. 上海恢复后做反向复制（广州主 → 上海新从），同步完成后择期切回（通常半夜低峰）

## 五、数据备份 & 恢复（7 层备份链）

### 5.1 备份策略表

| 备份对象 | 频率 | 保留期 | 存储位置 | 加密 |
|---|---|---|---|---|
| MySQL 全量物理备份（Percona XtraBackup） | 每日 02:00 | 30 天 每日 + 12 个月 每月 1 号 | COS 上海 + COS 广州 + OSS 杭州（3 副本） | GPG AES-256 |
| MySQL binlog 增量 | 每 5 分钟 push | 90 天 | COS 上海 | SSE-S3 + GPG |
| Redis RDB + AOF | 每小时 RDB + 实时 AOF | 7 天（可从 MySQL 重建） | 本地 + COS 上海 | AOF 加密 |
| COS 文件（合同/回单/扫描件） | 实时双写上海+广州，1 小时后 OSS 跨云复制 | 永久 + 版本控制 90 天回滚 | COS 上海 + COS 广州 + OSS 杭州 | SSE-S3 |
| 前端 ZIP 版本归档 | 每次发布 | 永久 | COS 上海 `versions/` | GPG |
| 系统配置（K8s manifest / Nginx conf / DNS 记录） | 每次变更提交 Git，每日导出 | 永久 | Git 私有库 + COS 上海 | SSH Key + GPG |
| 审计日志（log_admin_* 5 张表） | 每日导出 JSON | 永久（合规要求） | COS 上海 归档桶 | GPG + 写一次读多次（锁定桶 WORM） |

### 5.2 备份校验（每周 必跑，不能只备份不验证）

```shell
# 每周一 03:00 自动跑下面这套（Jenkins / 云工作流）：
1. 拉最新周日全量备份 + 截止周一 00:00 的 binlog
2. 新起临时 MySQL 实例（空实例，不碰生产）
3. XtraBackup --prepare → 导入 → 回放 binlog 到 00:00 点
4. 对比 3 个校验集合：
   - 财务流水总行数 == 生产快照行数（允许 binlog 时差 5 分钟内）
   - 上月关账凭证 hash == 生产 hash（财务数据绝对不能差）
   - 10 条随机订单 + 10 条考勤 + 10 条花名册 == 生产快照
5. 校验全通过 → 发送企业微信群"✅ 本周备份校验通过"
6. 校验失败（任何一条差）→ P0 告警 + 电话打醒运维 + 暂停后续所有变更
```

### 5.3 误操作回滚（删错数据 / 改坏数据）

| 场景 | 恢复方法 | RPO |
|---|---|---|
| DELETE 忘加 WHERE 清空整张表 | 最近一次 binlog 位点 + STOP_BEFORE 回放到误操作前 | 15 分钟 |
| UPDATE 批量改错（如全员日工资改 0 元） | 同上，binlog 回滚 + 审计日志定位误改字段范围 | 15 分钟 |
| 误删了整月考勤（2026-07） | 备份快照捞 7 月数据 INSERT 回来，和 8 月新数据合并 | 30 分钟 |
| 误作废了 50 张财务凭证 | 作废凭证本身"保留流水 + 关联相关ID"，重新做红字冲销 + 补正确凭证，**不要物理恢复覆盖**（防止再错一次） | 1 小时人工 + 自动化脚本 |

## 六、容灾切换 Playbook（runbook，运维 P0 级必读）

### 6.0 灾难级别定义

| 级别 | 定义 | 触发响应 |
|---|---|---|
| **P0 紧急** | 上海双 AZ 全挂 + 主从 DB 全不可用 / 前端打不开 / 财务无法结账 | 全员拉会 + 10 分钟内启动 6.2 跨地域容灾切换 |
| **P1 高危** | 单个 AZ 挂 / 主 DB 切换过一次但业务仍可用 / EdgeOne Pages 上海地域故障已自动切新加坡 | 运维单干，30 分钟内查明原因，1 小时内恢复，业务群滚动播报进度 |
| **P2 一般** | 某个边缘接口 5xx 超 5% / 考勤 ISAPI 门禁断连 / 文件上传偶尔失败 | 当班工程师处理，24 小时内修复 |

### 6.1 P1 单 AZ / 主库宕机切换 Runbook

> **目标 RTO：≤ 30 分钟**

```
T+0    监控告警响起（P1 微信 + 短信），确认主库 / AZ 真的挂了
T+1min 运维登录云控制台
T+2min 腾讯云 MySQL 高可用版 → 点「主从切换」（如已自动切，跳过）
T+5min 检查新主的 SHOW REPLICA STATUS（旧主重启后当从用）
T+6min 检查 Redis：节点是否过半（cluster info 看 cluster_state:ok）
T+10min 跑冒烟脚本：
         .\_smoke_check.ps1 -BaseUrl "https://admin.your-troupe.com" -SkipLoginPrompt -UsePresetSession
         看 14 页 × 3 指标 → CSV 报告全 PASS
T+15min 前端 5 个关键操作：登录 → 客户列表 → 考勤日打卡 → 财务日流水 → 退出
T+30min 发业务群"✅ P1 故障已恢复，主库已切换至 {新IP}，业务无数据丢失"
T+24h  复盘文档输出（5 个 Why + 改进项 + 责任人 + DDL）
```

### 6.2 P0 跨地域容灾切换 Runbook（上海 → 广州）

> **目标 RTO：≤ 1 小时**；**RPO：≤ 15 分钟**

```
T+0     连续 3 个独立监控源（Prometheus/DNSPod健康检查/人工）同时判定上海全不可用
T+2min  拉紧急会议：运维 + 开发负责人 + 业务负责人（团长/财务）+ 云厂商 TAM
T+3min  广州：
         ① 启动冷备 K8s Deployment（replicas=2 从 0→2）
         ② MySQL 广州灾备从库 → 控制台点「提升为主」（写入 + 关闭只读）
         ③ Redis 广州集群 → 解除只读
T+8min   广州 API Ready（K8s 全部 Running），手动调 3 条冒烟
T+10min  回放上海最后 15 分钟 binlog（最坏 RPO 5 分钟丢失）
T+15min  DNSPod：admin.your-troupe.com 和 api.your-troupe.com 两个域名 CNAME 全部切广州
         TTL = 60（最快传播）
T+25min  全国 4 个探测点拨测（腾讯云拨测/17CE）确认 95%+ 地区返回广州 IP
T+30min  全量冒烟 14 页 PASS → 通知业务团长 + 财务："系统切换完成，可继续业务，RPO 15 分钟，期间如有 5 分钟数据请补充"
T+60min  出灾备切换报告（切换时间点 / RPO实测 / RTO实测 / 丢失数据清单 / 补录责任部门）

------- 上海恢复后 择期切回（半夜 02:00 低峰） -------
T+?h    上海新 MySQL 做广州主的从库，Seconds_Behind_Master = 0 连续 10 分钟
        → 停 2 分钟业务 → 反向切上海主 → 广州降为灾备从 → DNSPod 切回 → 启业务
        → 全程 < 5 分钟中断（安排 02:00-05:00 之间，通知客户"系统维护"）
```

## 七、安全 & 合规加固（配合 E-2 鉴权文档使用）

| 领域 | 要求 | 实施位置 |
|---|---|---|
| HTTPS | TLS 1.2+，禁用 SSLv3/TLS1.0/TLS1.1；HSTS max-age=31536000 | EdgeOne 配置 / Nginx ssl_protocols |
| 防爬虫 | WAF 规则 + RateLimit + User-Agent 黑名单 + JS 挑战（EdgeOne 内置 Bot 管理） | EdgeOne WAF + 业务后端 Redis 令牌桶 |
| 财务不可篡改 | fin_ledger_v1 所有「已对账」凭证写入后，**禁止 UPDATE / DELETE**，只能红冲（新增一条负数凭证关联原 ID） | 后端中间件层强制拦截，MySQL 层面再给 role_finance 无 DELETE 权限（只有 INSERT/SELECT） |
| 备份合规 | 审计日志 `log_admin_*` 导出到 COS 归档桶 + WORM（Write Once Read Many，锁定 10 年），满足《会计档案管理办法》30 年保留 | COS WORM 策略 + 跨地域复制 |
| 密码/密钥管理 | bcrypt cost=13、所有密钥（COS AK/SK、DB 密码、RSA 私钥）放 腾讯云 KMS / 阿里云 KMS，禁止写代码/配置文件明文 | KMS + 环境变量 + K8s Secret + CI 加密注入 |
